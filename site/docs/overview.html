Overview

Welcome!

This page aims to provide an overview about everything you need to know about VMSeal.

{% include icon.html icon="features" %} Features

  • Security is built-in, not bolted-on.
  • Native-first -- written in Swift.
  • Handcrafted -- no LLMs are involved.

See more about security below.

{% include icon.html icon="installation" %} Installation

There are currently no downloads available, and you thus have to build it yourself.
Once the app is notarised, binaries will be distributed.

Please note that the app only supports ARM-based Macs.
Intel Macs may get limited supported if there is demand.

{% include icon.html icon="security" %} Security

In VMSeal, security is a core tenet, so read more about how the different aspects contributes to the whole security model below.

{% include icon.html icon="threat-model" %} Threat Model

The app treats its guests as if they are untrusted, but not necessarily compromised.
The host, however, is assumed to be fully trusted.

It is fundamentally impossible to distrust the host due to the fact that VMSeal is a type-2 hypervisor.

{% include icon.html icon="sandboxing" %} Sandboxing

The app has two layers which are treated differently in this regard; the VM service (provided by the system), and the "frontend" (i.e. VMSeal).

{% include icon.html icon="frontend" %} Frontend

The front-end to the VM service is sandboxed via macOS' App Sandbox.
Nothing is requested from inside the sandbox, except for outgoing connections, which is only used for downloading VM images.

Besides the App Sandbox, VMSeal's frontend utilises several of the following hardening features:

  • Hardened Runtime
  • MTE (only applicable on select M-series chips)
  • PAC
  • and more...

{% include icon.html icon="vm-service" %} VM service

The Virtualization.framework launches a dedicated VM service which is where the VM actually is contained inside.
This service shows up in Activity Monitor and is sandboxed.

{% include icon.html icon="source-code" %} Source Code

Swift is the primary and preferred language inside the source code.
Low-level languages like C are avoided.

There are also no dependencies besides official Apple libraries.

This is due to supply-chain risks inherent when relying on third-party dependencies, thus we don't trust any parties besides Apple themselves.

The source code itself encourages audits, and effort gets put into making it maintainable, thus more easily auditable.

{% include icon.html icon="the-user" %} The User

The user is considered a threat, in the way that they may make mistakes.
Hence, we don't really permit much customisation or similar.

For example, the supported OS used and its bootable image is currently hardcoded into the source-code;
there is no way for the end-user to change it without forking it, and that is a feature, not a bug.

{% include icon.html icon="the-guest-os" %} Guest OS

As briefly mentioned in the previous section, VMSeal hardcodes the OS to be used into the source-code.
We use an in-house OS dubbed "VMSeal/OS" which is an Alpine-derived Linux distribution, which features a significantly hardened kernel.

Tonnes of unnecessary drivers and other features are disabled by default to reduce attack surface.
Kernel hardening options disabled by the upstream are re-enabled here, like hardened memory initialisation, etc.

{% include icon.html icon="privacy" %} Privacy

No data is collected by VMSeal whatsoever, and it will never do so either.
